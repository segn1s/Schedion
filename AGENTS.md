# Правила работы для команды и ИИ-ассистентов (AGENTS.md)

Данный документ определяет стандарты разработки, архитектурные требования и правила взаимодействия для участников команды проекта **Schedion** и привлекаемых ИИ-агентов. Все разработчики (включая AI-инструменты) обязаны соблюдать эти правила.

---

## 1. Архитектура и проектирование

1. **Архитектурный паттерн:**
   - Весь код проекта должен следовать архитектуре **MVVM** (Model-View-ViewModel).
   - UI строится на **Jetpack Compose** и Material 3.
   - Состояние экранов (UI State) хранится во `ViewModel` и передаётся в Compose через `StateFlow` / Compose State.
   - Compose-функции по возможности должны быть stateless; практикуйте State Hoisting (подъём состояния).

2. **Принципы SOLID и DRY:**
   - Соблюдайте принципы SOLID и DRY.
   - **Не создавайте лишних абстракций:** интерфейсы и слои должны появляться только тогда, когда это действительно необходимо (например, для тестируемости или замены реализации), а не про запас.

3. **Читаемость и именование:**
   - Названия функций, классов и методов должны чётко и однозначно выражать их назначение.
   - Если назначение функции/метода не очевидно из названия и сигнатуры, перед ним **обязательно** добавляется краткий комментарий-пояснение (KDoc).
   - В Compose-компонентах параметр `modifier: Modifier = Modifier` должен идти первым среди необязательных параметров.

---

## 2. Управление зависимостями и версиями

1. **Версии библиотек и инструментов:**
   - Использовать только **стабильные версии** библиотек и инструментов, гарантированно совместимые между собой. Использование версий `alpha`, `beta`, `rc` или `snapshot` допускается **только** после согласования с руководителем проекта (@segn1s).
   - Все зависимости и плагины объявляются централизованно через **Gradle Version Catalog** (`gradle/libs.versions.toml`).

2. **Требования к SDK:**
   - `targetSdk` и `compileSdk` должны соответствовать **последней стабильной версии Android** (на текущий момент — API 37, Android 17).
   - Перед любым изменением версий SDK обязательно сверяйтесь с официальной документацией [Android Developers](https://developer.android.com) и проверяйте совместимость с используемыми плагинами и библиотеками. **Запрещено угадывать номера версий.**
   - **Запрещено понижать** версии библиотек, `minSdk` или `targetSdk` без предварительного явного согласования с руководителем проекта.

3. **Обоснование новых зависимостей:**
   - Запрещено добавлять внешние зависимости без веской причины.
   - При добавлении любой библиотеки в описании PR и коммита необходимо подробно указать:
     1. Какую именно задачу решает библиотека.
     2. Почему выбрана именно она.
     3. Почему невозможно или неудобно использовать стандартные средства Android SDK / Compose или написать собственное решение.

---

## 3. Требования к ИИ-агентам и сгенерированному коду

1. **Исследование перед изменением:**
   - Перед внесением правок ИИ-агент обязан тщательно изучить существующий код, структуру проекта, соглашения и стили.
   - Не трогать несвязанные файлы (unrelated files) и не форматировать чужой код без прямой необходимости.

2. **Ответственность за качество:**
   - Код, сгенерированный ИИ, **не считается автоматически правильным**.
   - Автор Pull Request несёт полную персональную ответственность за проверку, сборку, тестирование и глубокое понимание каждого добавленного или изменённого участка кода.

3. **Прозрачность авторства (AI Disclosure):**
   - Если более **70% кода в коммите** написано ИИ-ассистентом, в теле сообщения коммита (commit body) должна присутствовать отдельная строка:
     ```text
     AI-assisted: more than 70% of code in this commit
     ```
   - Запрещено выдумывать фиктивные имена, адреса электронной почты или несуществующие GitHub-аккаунты ИИ и создавать фиктивные трейлеры `Co-authored-by`.

4. **Архитектурная стабильность:**
   - Не изменять глобальную архитектуру, публичные контракты интерфейсов и конфигурацию проекта без предварительного обсуждения.
   - Любые значимые технические решения должны быть детально аргументированы в PR.

---

## 4. Безопасность и секреты

1. **Защита конфиденциальных данных:**
   - Категорически запрещено хранить и коммитить в Git любые секреты, пароли, API-ключи, токены доступа, keystore-файлы и персональные данные.
   - Локальные настройки и пути к SDK должны находиться в `local.properties` (добавлен в `.gitignore`).
   - Для сборки и CI использовать GitHub Actions Secrets и переменные окружения, не логируя их значения.

---

## 5. Процесс разработки, Git и Pull Requests

1. **Ветки и задачи:**
   - Прямой коммит и пуш в ветку `main` запрещены (действуют правила защиты ветки).
   - Разработка ведётся в отдельных ветках:
     - `feature/<issue-number>-<short-description>` — для новой функциональности;
     - `bugfix/<issue-number>-<short-description>` — для исправления ошибок;
     - `refactor/<short-description>` — для рефакторинга;
     - `chore/...` или `ci/...` — для настройки инфраструктуры.
   - Если задача заведена в GitHub Issues, Pull Request **обязан быть привязан к Issue** (например, с ключевым словом `Closes #123` или `Fixes #123`).

2. **Сообщения коммитов (Conventional Commits):**
   - Использовать префиксы: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`, `ci:`.
   - Заголовок краток (до 72 символов), пишется в повелительном наклонении.

3. **Обязательные проверки перед оформлением PR:**
   - Перед отправкой PR разработчик обязан локально запустить и проверить:
     ```bash
     ./gradlew testDebugUnitTest
     ./gradlew lintDebug
     ./gradlew assembleDebug
     ```
   - В описании PR обязательно заполняются все разделы [шаблона PR](.github/pull_request_template.md):
     - **Что изменено**
     - **Зачем**
     - **Как проверено**
     - **Связанные задачи**
     - **Использовались ли ИИ-инструменты**

4. **Ревью и слияние:**
   - Для слияния в `main` требуется минимум одно одобрение от руководителя проекта (@segn1s), назначенного Code Owner (`.github/CODEOWNERS`), и успешное прохождение всех проверок CI.
